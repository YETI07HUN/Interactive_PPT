🧪 Unit 01 / 07

Unit tesztelés

🧪

Mi ez?

Az alkalmazás legkisebb önálló egységeit teszteljük izoláltan — egy függvényt, osztályt vagy modult —, anélkül, hogy a többi résztől függnénk.

Mikor?

A fejlesztés legelejétől kezdve, minden egyes függvény megírásakor. Ideálisan TDD (test-driven) megközelítéssel: előbb teszt, aztán kód.

Fejlesztés közben TDD Minden commitnál

Miért?

A hibák legolcsóbban itt foghatók meg. Egy elrontott számítás azonnal látszik, nem kell a teljes rendszert futtatni. Dokumentálja az elvárt viselkedést.

Hogyan? – Példák a DTT projektből

Teszteljük pl. a kalkulátor függvényeket (összeadás, osztás nullával), a validációs logikát (e-mail formátum, jelszóerősség), az árazási számításokat. Minden egységhez: bemenet → várt kimenet → tény kimenet.

Jest Vitest Mocha Jasmine PHPUnit
⚙️ Funkcionális 02 / 07

Funkcionális tesztelés

⚙️

Mi ez?

Ellenőrzi, hogy a rendszer funkcionálisan teljesíti-e a specifikációt. Nem az implementációt nézzük, hanem azt, hogy a felhasználói igény kielégül-e.

Mikor?

Minden sprint végén, új feature elkészültekor, és release előtt kötelezően. Folyamatosan, de a sprint review előtt különösen fontos.

Sprint végén Release előtt Új feature

Miért?

Megmutatja, hogy a gomb valóban azt csinálja-e, amit ígért. A specifikáció és a valóság közötti rés itt derül ki — nem az éles indítás után.

Hogyan? – DTT kontextusban

Minden egyes felhasználói műveletet szimulálunk: bejelentkezés, tankönyv keresés, fejezet megnyitás, kvíz beküldés. Teszteseteket írunk: bemenet → várt kimenet → tényleges kimenet. Manuálisan és automatizáltan is elvégezhető.

Cypress Selenium Playwright Postman (API)
🖥️ UI / UX 03 / 07

UI / UX tesztelés

🖥️

Mi ez?

Vizsgálja, hogy az interfész intuitív-e, a navigáció logikus-e, és a felhasználó megtalálja-e, amit keres — valós emberek bevonásával.

Mikor?

Amikor a funkciók már működnek, de a dizájn még finomítható — prototípus fázisban, beta verzióban, és minden redesign után.

Prototípus Beta verzió Redesign

Miért?

Kideríteni, hogy egy külső felhasználó — például egy diák — érti-e a navigációt, és 30 másodpercen belül el tud-e végezni egy alapfeladatot.

Hogyan? – DTT kontextusban

Valódi diákokkal végzett usability session: feladatok kiadása megfigyelés mellett. Hőtérképek a kattintási mintákhoz, eye-tracking a figyelem eloszlásához. Kérdés: „Meg tudja nyitni a kvízt 30 mp alatt?" — ha nem, az interfész átgondolást igényel.

🔄 Regressziós 04 / 07

Regressziós tesztelés

🔄

Mi ez?

Minden módosítás után az összes korábbi funkciót újra lefuttatjuk, hogy megbizonyosodjunk: az új kód nem rontott el semmit, ami korábban működött.

Mikor?

Minden egyes bugfix, új feature vagy frissítés után — automatikusan, minden commit érkezésekor a CI/CD pipeline részeként.

Bugfix után Új feature Minden merge

Miért?

A rejtett törések elkapásáért: egy látszólag ártatlan módosítás megronthat egy tőle független funkciót. Megelőzi, hogy éles rendszerben derüljön ki.

Hogyan? – DTT kontextusban

Automatizált test suite, amely minden commit után lefut. Ha a bejelentkezés módosul, automatikusan újra fut a tankönyv-lista, a keresés és a kvíz is. Egy gombnyomással ellenőrizhető, hogy semmi sem tört el.

📱 Reszponzivitás 05 / 07

Reszponzív tesztelés

📱

Mi ez?

Ellenőrzi, hogy az oldal minden képernyőméreten helyesen jelenik-e meg és használható-e — telefonon, tableten, laptopon és nagy monitoron egyaránt.

Mikor?

A vizuális elemek elhelyezése után, az élesbe állítás előtt. Minden layout-módosítás után, és új eszközcsaládok megjelenésekor.

Mobil Tablet Desktop 4K monitor

Miért?

A DTT diákok többsége mobilon éri el a tananyagot. Ha az oldal telefonon összetörik, a tartalom elérhetetlenné válik a célközönség számára.

Hogyan? – DTT kontextusban

Chrome DevTools különböző eszköz-szimulációkkal, valós telefonon manuális ellenőrzés, BrowserStack cross-browser tesztelés. Fő szempontok: szövegméret, gombok érinthetősége, képek méretezése és a layout töréspontjai (breakpoints: 480 / 768 / 1024 / 1440 px).

Chrome DevTools BrowserStack Responsively Safari iOS
🔗 Integrációs 06 / 07

Integrációs tesztelés

🔗

Mi ez?

Ellenőrzi, hogy a rendszer különálló moduljai együtt is helyesen működnek-e — az egységek közötti adatáramlást és kommunikációt teszteli.

Mikor?

Miután az egyes modulok unit-teszteken átmentek, és össze kell őket kötni: frontend ↔ backend, backend ↔ adatbázis, külső API csatlakozásakor.

Modulok összekapcsolásakor API integráció

Miért?

Az egységek önmagukban működhetnek, de együtt hibásak lehetnek. Pl. a frontend jó adatot küld, de az API formátuma nem egyezik — ez csak integrációs teszttel derül ki.

Hogyan? – DTT kontextusban

Teszteljük a bejelentkezés → tankönyv lista betöltés → fejezet megnyitás teljes folyamatát. Ellenőrizzük, hogy az adatbázisból jött tananyag helyesen jelenik-e meg a frontenden. API végpontokat valódi kérésekkel teszteljük, és figyeljük a hibakezelést.

🔐 Biztonsági 07 / 07

Biztonsági tesztelés

🔐

Mi ez?

Feltárja az alkalmazás biztonsági sebezhetőségeit — jogosulatlan hozzáférés, adatszivárgás, injekciós támadások — mielőtt egy valódi támadó megtenné.

Mikor?

A fejlesztés egész folyamán — nem csak az élesítés előtt. Különösen fontos bejelentkezési rendszer, adatkezelés, vagy fizetési modul hozzáadásakor.

Auth fejlesztésekor Élesítés előtt Rendszeresen

Miért?

A DTT diákok személyes adatait kezeli. Egy szivárgás vagy jogosulatlan hozzáférés nemcsak jogi kockázat, hanem a felhasználók bizalmának elvesztése is.

Hogyan? – DTT kontextusban

Teszteljük az SQL injection-t (pl. bejelentkezési mezőknél), XSS-t (szkript injektálás), a CSRF-védelmet és az autentikációs tokenek biztonságát. Ellenőrizzük, hogy csak bejelentkezett felhasználók érhetik el a tananyagot, és a jelszavak hashelve tárolódnak.

OWASP ZAP Burp Suite npm audit Snyk
